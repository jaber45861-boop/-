## 1. Registration schema (Phase 1)

Conceptual structure per directive: identity → source → mode → behavior → tools → adapter → activation status → validation status.

### 1.1 Fields and H1–H7 mapping

| Registry column | Extension Contract field (`03` §4) | Rule |
|---|---|---|
| Command | `command` (H1, H3 unique) | verbatim from `08` §4 v3 command column |
| Name | `name` (H1) | source name; `—` = empty-but-present (H1: "required even if empty") — never invented |
| Purpose (source) | `purpose` (H1) | verbatim source purpose |
| Trigger | `trigger` (H1) | the legacy key chord / syntax, recorded not bound |
| Behavior + Mode | `behavior` (H1, H2) | source behavior + a `04` §2 Core mode (or explicit exemption) |
| Output | `output` (H1) | source-declared result |
| Tools | `requires.tools` (H1, H5) | declared or `none` |
| Adapter | (binding metadata) | `§4` declaration id when the adapter isolates legacy behavior |
| Source | (traceability, HK-08) | `file:line` anchors, validated against the working tree |
| Activation status | §1.2 | one of seven directive statuses |
| Validation status | §1.3 | registration-readiness derived from activation status |

### 1.2 Activation statuses (the seven)

| Status | Meaning | Execution rule |
|---|---|---|
| `ACTIVE` | Validated, unblocked registration; binding enabled in this dataset | may be enabled by a conformant runtime without further rulings or components |
| `ADAPTER_REQUIRED` | Legacy operation isolated behind an adapter (§4) | must NOT enable until the adapter exists — VALIDATE fails closed |
| `BLOCKED_CONFLICT` | Source self-contradicts; meaning preserved | must NOT execute — awaiting executive ruling (`13`) |
| `BLOCKED_AMBIGUOUS` | Identity/behavior overlap; nothing inferred | must NOT execute — awaiting executive ruling (`13`) |
| `BLOCKED_INSUFFICIENT_INFO` | H1 fields not derivable from source | must NOT execute — awaiting evidence (`13` §Evidence requests) |
| `HISTORICAL_REMOVED` | Removed/renamed in source; kept for history | never exposed as a command; never deleted from this registry |
| `METADATA_ONLY` | Not a Grimoire command (grouping notation, trigger syntax, external-tool key) | informational; never registered as a command |

### 1.3 Validation statuses

`VALIDATED` (H1–H7 statically satisfied from source) · `PENDING_ADAPTER` (schema valid; adapter missing) · `PENDING_RULING` (awaiting `13` decision) · `PENDING_EVIDENCE` (awaiting `13` evidence request) · `NOT_APPLICABLE` (record-only: historical/metadata rows).

### 1.4 Activation determination for the 14 compatible hotkeys (Phase 2 condition)

The directive permits `ACTIVE` only if the Extension Contract permits activation without additional runtime dependencies. Checked against the contract:

1. `03` §4 H1–H7 for these 14 are **statically satisfiable from source alone** — all seven fields present, every mode ∈ `04` §2 nine modes, commands unique (H3), no Core file touched (H4), bindings are L3 assets (H7).
2. `03` §8 mandates no storage format — this dataset registers them without Core changes.
3. "Additional runtime dependency" tested per hotkey: an **adapter** (none of the 14 need one — that is the `ADAPTER_REQUIRED` class), a tool beyond the universal Tool Bus (13 of 14 declare `tools: none`; `SoS` declares search providers in `requires.tools`, handled per H5 as a trigger-time blocked state, not a registration dependency), or an **executive ruling** (none of the 14 is outstanding).
4. Therefore the 14 are registered `ACTIVE`. Caveat, stated once and binding: *registry-active ≠ currently executing* — trigger-time execution still flows through the future Hotkeys module (`02` §6: module implementation is future work; GAP-007: no runtime in this repository). This task builds no runtime, per directive.
